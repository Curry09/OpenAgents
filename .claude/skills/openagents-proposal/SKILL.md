# OpenAgents 提案与文档房规

## 总则（其余规则都是它的推论）

> **表达的抽象层级必须严格高于代码。与代码同粒度的独立复述，无论用什么形式（伪代码 / 流程图 /
> 中文散文），都是负资产。**

它不只是没用，是**有害**：它跟代码说同一件事，而没有任何东西保证它俩一致。明天有人调换两个调用，
它就开始骗人，且不会有任何东西失败。

所以动笔前先问：**这句话，代码本身说得出来吗？** 说得出来 → **删掉它是净收益。别写。**

## 三层，各自的载体

| 层 | 它回答 | 载体 |
|---|---|---|
| **功能逻辑** | 产品替我做了什么 | 独立文档：一张上下文图 + 一组具体场景 |
| **行为逻辑** | 它什么时候会变成什么状态 | 独立文档：状态图（层级 + 正交，不是扁平 FSM） |
| **实现逻辑** | 怎么拆（目录 / 边界 / 接口）+ 怎么跑（内部） | **代码本身**：docstring / 签名 / 常量注释 / 会失败的测试 / 生成物。**不另存一份文档。** |

实现逻辑**要写清楚**——不写清楚，三个月后没人敢动分支顺序，也没人知道那个文件为什么不拆。
它只是**不该独立于代码存在**。

范本见 `example.md`（取自 `recipes/vigil.py` 的真实代码，三层各写一遍）。

---

### 1. 功能逻辑 —— 唯一真正面向非技术读者的一层

只写两样东西：

- **一张上下文图**：系统是一个盒子，画出它跟哪些外部角色 / 系统交互。**不画内部**——一画内部，
  受众就变成技术读者了，那是另一层的事。
- **一组具体场景**：`在什么情况下 → 发生什么`。用领域语言，**一个技术名词都不许出现**。

**必含一条：「它什么时候会来打扰我」。** 非技术读者最关心的就是这个。

写场景的正当理由是**逼作者在写的时候把话说准**，不是"非技术读者真会来读"。写"连着失败几次它就
停下来叫人"时，你必须回答"几次"——这个问题在散文里会被含糊过去。

**不要用大段散文描述功能。** 散文里，缺口和自相矛盾不会显形；条目会。

### 2. 行为逻辑 —— 状态图

有状态、有时序、有"什么时候会打扰人类"的东西（vigil 循环、合并流水线、RFC 生命周期）→ 画状态图。

- **层级**：复杂子流程折叠成一个状态再展开，不摊平进主图。扁平状态列表会指数爆炸。
- **正交**：两个独立演进的维度画成两条并行轴，**不做笛卡尔积**。
- **每条回环边必须标上限**。无上限的回环 = 活锁。
- **必须标出"唯一会打扰人的出口"**。找不到它，说明系统设计本身有问题。
- **图上每个护栏都要能在代码里指到具体那一行**（常量 / 索引 / 约束），否则它只是画着好看。

状态图的价值不在好看，在于**它逼你暴露漏掉的情况**——"等人审的时候又来了新评论怎么办？"这类分支
在散文里会被静悄悄漏掉。

### 3. 实现逻辑 —— 写，但写在代码里

它有**两个面**，性质完全不同，别混：

- **结构面**：怎么拆。目录分层、文件边界、模块职责、函数接口与签名。
  → **代码存在之前就要定**，是评审的主要对象——拆错了没法靠事后补注释救回来。
- **内部面**：怎么跑。为什么这么做、顺序与不变式、上限与阈值、断言。→ 跟着代码走。

代码能说出 what（这行在干什么）和 how（调用了谁）。它说不出下面这些，而这些正是实现逻辑的**全部**
价值。每一样都有固定落点，**都不新开文档**：

| 面 | 它说的是 | 落点 |
|---|---|---|
| 结构 | 边界切在哪、每个模块**藏起了哪个会变的决策** | spec 的 files 分配（设计时）→ 落地后归模块 docstring |
| 结构 | **为什么不那样拆**（否决掉的切法 + 理由） | 模块 docstring |
| 结构 | 接口契约：前置条件、副作用边界、纯不纯 | 函数签名（keyword-only）+ 函数 docstring |
| 结构 | 实际的依赖方向（谁 import 谁） | `spec graph` 生成的 `ARCHITECTURE.md`，**永不手改** |
| 内部 | 为什么这么做 / **为什么不用那个更显然的方案**（含前提、代价、换回去的成本） | 模块 / 函数 docstring |
| 内部 | 哪些顺序、哪些不变式是正确性依赖，破了会出什么症状 | 函数 docstring |
| 内部 | 为什么需要这个上限 / 阈值往哪边偏、偏错了会怎样 | 常量注释 |
| 内部 | 一条重要且可判真假的断言 | **让它在为假时构建失败**：测试 / schema 约束 / CI 闸 |

**结构面的两条判据**（拆分唯一站得住的两条，其余都是口味）：

1. **按「会变的决策」拆，不按「流程步骤」拆。** 每个模块必须能一句话答出：**我藏起了哪个可能会变的
   决策？**（换编码 agent / 换队列存储 / 换 GitHub 的调法）答不出 → 它不是模块。
   **文件列表读起来像一串流程步骤**（`sense.py` / `classify.py` / `act.py`）**不是拆分，是把一个
   函数摊成三个文件**。真正的边界是「换掉它时，别人不用改」的那条线。
2. **深模块：简单接口 + 大量功能。** 拆出来的东西如果只是转发一层、或者接口复杂度接近实现复杂度，
   那是**浅模块**——付了拆分的成本，却没换来任何隐藏。**判据是接口/实现的复杂度比，不是行数。**
   "这个文件太长了所以拆一下"**不是**理由。

**一条边界值不值钱，看「换掉被它藏起来的那个决策，要改几处」**，并且这句话要写下来——它是可证伪的。

**函数接口**（本仓规范，见 CLAUDE.md）：keyword-only，禁位置参数；private 函数参数禁默认值，调用方
必须显式传参。目的是**让接口的意图在调用点就可见**，而不是要跳进定义才知道传的是什么。签名之外的
契约（**副作用边界、纯不纯**）写进 docstring——这两样看代码是看不出来的（看不出的正是"以后也不许有
别的"这层意思）。

**为什么落点是代码，不是一份文档。** 一致性不是靠纪律维持的，是靠"只有一个东西"构造出来的。所以：

- `ARCHITECTURE.md`（`spec graph` 从 import 图 + docstring 生成）和 `OVERVIEW.md`（`spec render`
  生成）**永不手改**。要让实现逻辑更好读，去改 docstring / 命名 / 代码结构，让**生成物**变好。
- 想写"XX 模块的工作原理"时，先在上表里找这段话的落点。找得到 → 写进那个落点。找不到 → 它只是把
  调用顺序又抄了一遍。
- **一份更好的文档救不了理解问题**。这套规则的存在不是让你多写文档，而是让你**少写、写在对的层级、
  剩下的交给代码自己去证明**。

## Review 闸

diff 里出现任何文档 / 注释 / 图，逐条过：

| 检查 | 通过条件 |
|---|---|
| 总则 | 它说了代码说不了的话。说不出 → 删 |
| 层级 | 场景条目里 0 个技术名词；状态图有层级 + 正交 + 回环上限 + 唯一打扰人的出口 |
| 实现逻辑落点 | 落在 docstring / 签名 / 常量注释 / 测试 / 生成物之一，**没有新开的实现说明文档** |
| 结构 | 每个新模块答得出"我藏起了哪个会变的决策"；不是按流程步骤切；不是浅模块 |
| 生成物 | `ARCHITECTURE.md` / `OVERVIEW.md` 是重新生成的，不是手改的 |
| 注释 | 只写约束和 why，不解释"这行在做什么" |
| 断言 | 重要的断言变成了会失败的测试 / 闸门，而不是一句没人能证伪的话 |
| 诚实 | 没有声称图或状态机"有研究支持"——它没有 |
