# SAP 标杆例子

一个主题写三遍：**守夜循环 vigil**。所有材料取自 `openagents/recipes/vigil.py` 的真实代码，未虚构。

三块各自回答一个问题、面向一批不同的读者，**载体也不同**：

| 层 | 回答 | 载体 | 本例成品 |
|---|---|---|---|
| 功能逻辑 | 产品替我做了什么 | 上下文图 + 场景条目 | 下面第一块 |
| 行为逻辑 | 它什么时候变成什么状态 | 状态图（层级 + 正交） | 下面第二块 |
| 实现逻辑 | **怎么拆**（目录 / 文件边界 / 接口）+ **怎么跑**（内部） | **代码自己**：docstring / 签名 / 常量注释 / 会失败的测试 / 生成物 | 下面第三块 |

第三块不是"不写"，是**不另存一份**——写在代码里，跟着代码一起改，改错了 CI 会红。

---

## 一、功能逻辑 —— 上下文图 + 场景清单

**受众**：非技术读者。这是唯一一层真正为他们存在的——**一画内部，受众就变成技术读者了**。

**它是什么**（一张上下文图：一个盒子 + 外部角色 + 交互，不画内部）：

```
        ┌──────────────┐  读 issue / 提 PR / 发评论   ┌────────────┐
        │  维护者(人)  │ ←─────────────────────────→ │   GitHub   │
        └──────┬───────┘                             └─────▲──────┘
               │ 只做两件事：                              │
               │ ① 提 issue  ② 给 PR 点同意                │ 全部协作
               ↓                                           │ 都发生在这里
        ┌──────────────────────────────┐                   │
        │        OpenAgents 守夜       │ ──────────────────┘
        │  「你睡觉时，它替你把 issue  │
        │    做成待你审核的 PR」       │ ←── 调用 → Claude Code / Codex …
        └──────────────────────────────┘         （背后的编码 agent）
```

**它做什么**（场景清单：`在什么情况下 → 发生什么`，零技术名词）：

- 仓库里有人提了个 issue → 守夜自己领走，写代码，提一个 PR，并在 issue 下留言说做完了。
- 这个 issue 得等另一个 issue 先做完 → 守夜自己看得出来，**先不动它**，等前置的合并了再开工。
- PR 提了但测试没过 → 它自己看报错、自己改、重新提交，**不需要人管**。
- 同一件事连着失败三次 → 它**停下来**，标记"需要人"，并说明卡在哪。**这是它唯一会打扰你的时候。**
- 有人在 PR 下留了评论 → 它读评论、改代码、回复"已按你说的改了"。
- 一件事明明该有动静却半天没动静（比如测试根本没启动）→ 它也**停下来叫人**，而不是干等到天亮。
- 测试过了、评论也回完了 → 等**一个人**点同意，然后合并。**合并永远需要人点头。**
- 好几个 issue 互不相干 → 它同时开工；但**同一个 issue 上的事永远一件一件来**，不会自己踩自己。
- 半夜进程崩了 → 重启后**在飞的活不丢**，从断点接着做。

### 判据

| 检查 | 通过条件 |
|---|---|
| 技术名词 | 场景清单里出现 0 个实现词（tick / 队列 / SQLite / worker …） |
| 形式 | 是**条目**不是段落，每条形如「在什么情况下 → 发生什么」 |
| 主语 | 主语是产品，宾语是用户**能感知**的东西（PR、评论、"打扰你"），不是内部对象 |
| 必含 | 必须有"它什么时候会来烦我"这一条——非技术读者最关心的就是这个 |
| 图 | 只画一张：盒子 + 外部角色 + 交互。不画内部结构（那已是 Level 2，受众变了） |

写场景的正当理由是**逼作者把话说准**，不是"非技术读者会来读"。证据：写第 4 条时你必须回答
"失败几次算够"（答案 `_MAX_ATTEMPTS = 3`），这个问题在散文里会被含糊过去。

## 二、行为逻辑 —— 状态图

**受众**：需要知道"它现在在哪、下一步会去哪"的人。

两件武器：**层级**——把合并流水线折叠成一个可展开的子状态机；**正交**——「issue 的进展」和
「一件活在队列里的死活」是两条**独立演进**的轴，硬塞进一张扁平图就是灾难。

```
╔══════════════════════════════════════════════════════════════════╗
║ 轴 A：issue 的进展（人关心的）                                   ║
║                                                                  ║
║   [新 issue] → ┌────────┐  前置全合并  ┌────────┐                ║
║                │ 被挡住 │ ───────────→ │ 可开工 │                ║
║                └────────┘              └───┬────┘                ║
║                  ↑ 判定它依赖              │                     ║
║                    别的 issue              ↓                     ║
║                                       ┌──────────┐               ║
║                                       │ PR 已开出│ ←──┐          ║
║                                       └────┬─────┘    │ 打回     ║
║                                            │          │ 回环     ║
║                    ┌───────────────────────┴──────────┴───────┐  ║
║                    │ 合并流水线（层级：折叠的子状态机）        │  ║
║                    │   解冲突 → CI → e2e → 审查 → 合并        │  ║
║                    │   任一步失败 ────────→ 打回上一步重来     │  ║
║                    │   合并这一步：永远等人点同意              │  ║
║                    └────────────────────┬─────────────────────┘  ║
║                                         ↓                        ║
║                                    ┌────────┐                    ║
║                                    │ 已合并 │                    ║
║                                    └────────┘                    ║
╠══════════════════════════════════════════════════════════════════╣
║ 轴 B：一件活在队列里的命运（与轴 A 同时演进，互不干扰）          ║
║                                                                  ║
║   ┌────────┐  被领取   ┌─────────┐   做完    ✓ 出队              ║
║   │ 排队中 │ ────────→ │ 处理中  │ ────────→                     ║
║   └────────┘           └────┬────┘                               ║
║       ↑                     │ 失败／租约到期（进程挂了）         ║
║       └─────────────────────┤                                    ║
║         回队重试（< 3 次）  │ 第 3 次仍失败                      ║
║                             ↓                                    ║
║                     ┌──────────────┐                             ║
║                     │  需要人介入  │ ← 唯一会打扰人的出口        ║
║                     └──────────────┘                             ║
╚══════════════════════════════════════════════════════════════════╝
```

**这张图挣到的钱**：它的价值不在好看，在于**逼你暴露漏掉的情况**。下面每个问题都是被图问出来的，
散文里它们会被静悄悄漏掉——每一个都对应代码里一行真实的护栏：

- 轴 B 卡在"处理中"时进程崩了，轴 A 停在哪？→ 必须有租约回收（`CLAIM_LEASE_SECONDS = 3600`）。
- "打回回环"能回几次？→ 必须有上限（`_MAX_ATTEMPTS = 3`），否则毒丸活无限重试占槽。
- 同一个 issue 的两件活能同时处理吗？→ 不能（`subject` 列 UNIQUE，入队时结构性互斥）。
- "被挡住"的 issue 何时重新检查？→ 每轮重算当前态，不追事件，漏了也自愈（level-triggered）。
- 一个状态**永远不动**算不算故障？→ 算。故有看门狗（`_WATCHDOG_DEFAULTS` 按成因分档）。

### 判据

| 检查 | 通过条件 |
|---|---|
| 层级 | 复杂子流程必须**折叠成一个状态**再展开，不许摊平进主图 |
| 正交 | 两个独立演进的维度必须画成两条并行轴，**不许做笛卡尔积** |
| 出口 | 必须标出"唯一会打扰人的状态"。找不到它，说明系统设计本身有问题 |
| 回环 | 每条回环边必须标注**上限**。无上限的回环 = 活锁 |
| 落地 | 图上每个护栏都必须能在代码里指出**具体那一行**（常量 / 索引 / 约束），否则它是画着好看的 |
| 诚实 | **不许声称状态图"有研究支持、比文字好懂"**——它没有 |

## 三、实现逻辑 —— 写，但写在代码里

实现逻辑必须写清楚，否则三个月后没人敢动 `_classify` 的分支顺序，也没人知道那个文件为什么不拆。
**这一块规定的是它的落点**：不新开 `docs/vigil-internals.md`，而是落进五个**跟代码同生共死**的
载体。判定标准只有一条——**它说的话，代码本身说不出来吗？**

它有**两个面**，性质不同：

- **结构面**（怎么拆）：目录分层、文件边界、模块职责、函数接口。**代码存在之前就要定**，是评审
  的主要对象——拆错了没法靠事后补注释救回来。
- **内部面**（怎么跑）：为什么这么做、顺序与不变式、上限与阈值、断言。跟着代码走。

下面是本仓的五个真实成品：结构面一个，内部面四个。

### 载体一 · 结构 —— 写"边界切在哪，以及为什么不那样切"

**判据只有两条，其余都是口味。**

**判据 1：按「会变的决策」拆，不按「流程步骤」拆。** 本仓的包分层，每一层都能一句话答出
「我藏起了哪个会变的决策」：

```
openagents/
  backends/   ← 藏起「背后是哪个 CLI-agent」  claude_code.py / base.py（要接 codex、nexau）
  agents/     ← 藏起「提示词怎么写」          零逻辑的 Template：triager / implementer / reviewer …
  recipes/    ← 藏起「编排顺序」              纯控制流：vigil / stages / backfill
  runtime/    ← 藏起「怎么跑一个 agent」      engine / gates（硬闸）/ context / state
  utils/      ← 藏起「外部世界的形状」        github.py（REST 的形状）/ git.py / workspace.py
```

**注意这个文件列表读起来不像一串流程步骤**——没有 `sense.py` / `classify.py` / `act.py`。
那三个恰恰是 vigil 的三个流程步骤，而它们**同在一个文件里**：流程步骤不是模块边界，「换掉它时
别人不用改」的那条线才是。这条线在本仓是可检验的：换一个编码 agent 只动 `backends/`；换 GitHub
的调法只动 `utils/github.py`。

**判据 2：深模块 —— 简单接口 + 大量功能。** `vigil.py` 的模块 docstring 里，这条判据被用来
**否决一种拆法**（真实节选）：

> **只一个入口 `run_vigil`、只一个文件。** 守夜天生按「subject 为并发单元」调度，`concurrency`(=K)
> 是并发上限；**串行不是另一种模式，而是 `concurrency=1` 的退化**。故不拆 serial / parallel 两函数
> 两文件——那是把同一件事摊成**浅模块**。

以及边界质量的实测：**"换 Postgres 是局部替换、非重写——替换点收在 `_claim_next` /
`_reclaim_expired` / `_mark_done` / `_requeue_or_park` 四个函数里。"** 一条边界值不值钱，就看
**换掉被它藏起来的那个决策时，要改几个地方**。这句话是可证伪的：真去换，改超过四处就说明边界漏了。

**接口即契约。** 签名之外的部分写进 docstring——**副作用边界**和**纯不纯**是代码说不出的：

```python
def _sense(*, backend, state, config, subject, in_flight) -> _Observed:
    """**唯一的 GitHub 读**：把一个 subject 的现态收拢成一个不可变 `_Observed`。"""

def _classify(*, facts: _Facts, in_flight: bool) -> _Verdict:
    """纯函数：一个 `_Facts` → 四值判定。**这就是 reconcile 分支表本身**。

    护栏一（读 GitHub 上的 attempt 戳）**不在这里**——它有副作用，由生产者在外面包一层。
    本函数保持纯。
    """
```

"`_sense` 是唯一的读、`_classify` 保持纯"这件事，**看代码是看不出来的**（看不出来的正是"以后也
不许有别的"这层意思），但它是整个 level-triggered 模型能成立的前提。全 keyword-only、private
函数禁默认值（CLAUDE.md 规范）是同一个目的：**让接口的意图在调用点就可见**，而不是要跳进定义。

**实际的依赖方向不手画**：`ARCHITECTURE.md` 由 `spec graph` 从 import 图生成，谁真的 import 了谁
是可证伪的。手画一张"我们解耦了"的图，只是关于代码的一个断言。

### 载体二 · 模块 docstring —— 写"为什么不用那个更显然的方案"

`vigil.py` 的模块头（真实节选）。它没有一句话在复述调用顺序，全部篇幅在讲**被否决的方案**：

> **为什么感知是 level-triggered、不做变更检测。** 谓词**无历史**：不问「跟上一轮比变了没」，只问
> 「现在该不该动手」。进程若崩在「检测到 CI 变绿」和「真的去合并」之间，那个边沿就**永久消失**了——
> PR 会绿着躺到宇宙热寂。漏一个边沿 = 一个 PR 永久停摆。
>
> **为什么认领必须落 DB、不能用 GitHub label。** GitHub REST 对不安全方法**不支持条件请求**
> （*"Conditional requests for unsafe methods, such as POST, PUT, PATCH, and DELETE are not
> supported"*），且 label POST 是**追加**语义——两个并发认领**都会成功、都不报错**。即无 CAS，两个
> worker 会双跑同一个 PR。整文件 JSON 读改写同样会丢更新。DB 事务根治。
>
> **为什么 SQLite 而非 Postgres。** 本仓是单进程 K 线程，`BEGIN IMMEDIATE` 就是 Postgres
> `SKIP LOCKED` 的单机等价物，够用且零外部依赖。**代价写明**：SQLite 把部署钉在单机（跨网络文件
> 系统共享同一个库会**数据损坏**）。**换回去的成本也写明**：替换点收在 `_claim_next` /
> `_reclaim_expired` / `_mark_done` / `_requeue_or_park` 四个函数里，是局部替换、非重写。

它凭什么合规：内存队列 / GitHub label / JSON / Postgres 这四个方案**不在代码里**——代码只能告诉你
最后选了什么，永远不能告诉你为什么没选另外四个。它还记下了决策的**前提**（"单进程 K 线程"）、
**代价**（"钉在单机"）和**换回去的成本**（"收在四个接缝里"）：这是未来的人最需要、也最查不到的信息。

### 载体三 · 函数 docstring —— 写"哪些顺序是正确性依赖，不是风格"

`_classify` 的 docstring（真实节选）。分支表本身是**比代码高一级**的表达（代码是十一段
early-return，表是一张十一行的判定表），而它下面那三行才是真正无可替代的：

```
    ① merged / closed / needs-human ............... TERMINAL
    ② 最新评论是人发的（无我方签名）............... ACTIONABLE: reply
    ③ 依赖未全 merged ............................. QUIET(awaiting-blockers)
    ④ 还没有 PR ................................... ACTIONABLE: solve
    ⑤ mergeable_state = UNKNOWN / null ............ QUIET(awaiting-mergeability)
    ⑥ 冲突（mergeable_state = dirty）.............. ACTIONABLE: rebase
    ⑦ 当前 head 上 CI = pending / 零个 check ...... QUIET(awaiting-ci)
    ⑧ 当前 head 上 CI = failure ................... ACTIONABLE: fix-ci
    ⑨ e2e 证据缺失 / head_sha 陈旧 ................ ACTIONABLE: e2e
    ⑩ review 缺失 / 陈旧 / CHANGES_REQUESTED ...... ACTIONABLE: review-or-fix
    ⑪ 全绿 + APPROVED ............................. ACTIONABLE: merge

三处顺序是正确性依赖，不是风格（改动前先读这里）：
- ②在最前——人说「先别合，我有疑问」必须能抢在 merge 前面。合并不可逆。
- ⑤⑥在⑦前——冲突的 PR 拿不到 merge ref → GitHub 压根不给它任何 check → ⑦会把「零个 check」
  读成「CI 还在跑」，然后一直等到超时。不先挡住的话，症状是「CI 卡住了」，病因是「有冲突」。
- ⑦⑧只看当前 head_sha——否则会派 agent 去修已经修好的代码。
```

一个人读代码，能看出这十一支的顺序；**看不出哪三处顺序动了会出事、以及出事时长什么样**
（"症状是 CI 卡住，病因是有冲突"）。这就是代码说不出的话。

### 载体四 · 常量注释 —— 写"为什么需要这个上限"和"超限后的语义"

```python
# Spec-0065/T2: 同一 subject 领取-失败重排上限；超它不再回队、打 needs-human 交人。
# **这是唯一必须计数的护栏**——agent 崩/被 kill/租约过期时它没盖 attempt 戳、也没刷新任何 GitHub
# 时间戳，在 GitHub 上零痕迹：fp 判不出、age 也判不出，只能在队列行里数。
_MAX_ATTEMPTS = 3

# Spec-0065/T2: 看门狗阈值（秒），按 QUIET 成因分档。**宁可给宽**：设窄了会把正常在跑的 CI 误 park，
# 比不看门更糟；而 park 只是「打个 label + 贴条诊断」、完全可逆（人摘掉 label 系统立刻复活），
# 晚叫人的代价远小于误杀。
_WATCHDOG_DEFAULTS = {...}
```

注意这两条都不是在解释常量**是什么**（`3` 是三次，代码已经说了），而是在解释
**为什么非要有它**、**取值往哪边偏、偏错了会怎样**。

### 载体五 · 会失败的测试 —— 让重要的断言在为假时构建失败

一致性不靠纪律，靠"只有一个东西"。**一条断言重要到必须写下来，就让它在为假时构建失败**——这样它
才是实现逻辑，而不是关于实现的传说。本仓的对应关系：

| 想说的话 | 让它可证伪的形式 |
|---|---|
| "同一个 subject 的活是串行的" | `subject` 列 `UNIQUE` + 并发投递测试，断言处理不重叠 |
| "fp 的字段集 ≡ 分支表的输入集" | `_fingerprint` 哈希 `dataclasses.fields(_Facts)` **全集**（禁手写字段名列表）——加字段时不可能漏 |
| "agent 说做完了要真做完" | `assert_delivered` 硬闸：head 没前移就 raise |
| "e2e 真的跑了" | 证据溯源戳：`head_sha` 缺失 / 不匹配 → 硬 FAIL |
| "架构图跟代码一致" | `spec graph` 生成 `ARCHITECTURE.md` + CI 的 "Spec Validate & Drift" 闸 |

由此推出两条硬规矩：

- **`ARCHITECTURE.md`（`spec graph` 生成）和 `OVERVIEW.md`（`spec render` 生成）永不手改。** 想让实
  现逻辑更好读，去改 docstring / 命名 / 代码结构，让**生成物**变好。手改必然漂移，且会挂 drift 闸。
- **想写"XX 模块的工作原理"时，先找这段话在上面四个载体里的位置。** 找得到 → 写进那个载体。找不到
  → 说明它只是把调用顺序又抄了一遍：跟代码同粒度、没人能证伪、代码一改它就开始骗人。

### 判据

看到任何**描述代码**的手写产物，问一句：**"它说了代码说不了的话吗？"**

| 面 | 它说的是 | 落点 |
|---|---|---|
| 结构 | 边界切在哪、每个模块**藏起了哪个会变的决策** | spec 的 files 分配（设计时）→ 落地后归模块 docstring |
| 结构 | **为什么不那样拆**（否决掉的切法 + 理由） | 模块 docstring |
| 结构 | 接口契约：前置条件、副作用边界、纯不纯 | 函数签名（keyword-only）+ 函数 docstring |
| 结构 | 实际的依赖方向（谁 import 谁） | `spec graph` 生成的 `ARCHITECTURE.md`，永不手改 |
| 内部 | 为什么这么做 / 为什么不用那个更显然的方案（含**被否决的方案**、前提、代价、换回去的成本） | 模块 / 函数 docstring |
| 内部 | 哪些顺序、哪些不变式是正确性依赖，破了会出什么症状 | 函数 docstring |
| 内部 | 为什么需要这个上限 / 阈值往哪边偏 | 常量注释 |
| 内部 | 一条重要且可判真假的断言 | 测试 / schema 约束 / CI 闸 |

**结构面额外过两道**（拆分唯一站得住的两条判据）：

| 检查 | 通过条件 |
|---|---|
| 藏了什么 | 每个模块必须能一句话答出「**我藏起了哪个可能会变的决策**」。答不出 → 它不是模块 |
| 不是流程 | 文件列表**不许读起来像一串流程步骤**（`sense.py` / `classify.py` / `act.py`）——那是把一个函数摊成三个文件 |
| 深不深 | 接口复杂度 ≪ 实现复杂度。只做转发的一层 = 浅模块，拆了付出成本却没换来隐藏 |
| 边界成色 | 说得出「换掉被它藏起来的那个决策，要改哪几处」。改超过那几处 → 边界漏了 |
| 理由 | 「这个文件太长了」**不是**拆分理由。行数不是判据 |

## 五秒判定流程

```
要写一段面向人的逻辑描述？
  │
  ├─ "产品替我做了什么"？ ────────→ 第一块：上下文图 + 场景条目，零技术名词。
  ├─ "它什么时候变成什么状态"？ ──→ 第二块：状态图，层级 + 正交 + 标出唯一打扰人的出口，
  │                                 且每个护栏都能在代码里指到具体那一行。
  └─ "代码怎么做到的"？ ──────────→ 第三块：写进代码，不新开文档。落到五个载体之一：
        │
        ├─【结构面：怎么拆】代码存在前就要定，评审的主要对象
        │   ├─ 边界切在哪 / 藏了哪个会变的决策 ─→ spec 的 files 分配 → 模块 docstring
        │   ├─ 为什么不那样拆 ────────────────→ 模块 docstring（含否决掉的切法）
        │   ├─ 接口契约（副作用边界、纯不纯）─→ 签名（keyword-only）+ 函数 docstring
        │   └─ 谁 import 谁 ──────────────────→ spec graph 生成，永不手画
        │
        └─【内部面：怎么跑】跟着代码走
            ├─ 为什么 / 否决了什么 ──→ docstring（含被否决的方案、前提、代价）
            ├─ 顺序与不变式 ────────→ docstring（写清破了会出什么症状）
            ├─ 上限与阈值 ──────────→ 常量注释（写清往哪边偏）
            └─ 可判真假的断言 ──────→ 测试 / schema / CI 闸
```
