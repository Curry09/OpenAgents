# 软件设计哲学（多 Agent 系统适配）

本文档整理 Ousterhout《软件设计的哲学》（APoSD, 2018）的设计原则，并给出其在 OpenAgents 多 Agent
协作系统中的对应形式。组织依循原则间的逻辑关系而非原书章节次序；术语在首次出现处给出定义；括号内
章节编号标注出处。适用时机：RFC/spec 设计、模块边界与接口划分、错误模型确定，以及对既有设计的质量评估。

## 1. 核心命题

设计的首要目标是最小化接口消费者为理解与使用系统所需付出的认知成本。在多 Agent 系统中，接口消费者
有二：其一为承担宏观决策的人类监督者，其与系统交互的接口为 PR、评论与成果呈现；其二为后续接手任务的
Agent，其可用上下文受 context window 容量的硬性约束。任何设计决策均应先确定其接口消费者，再据以压缩该
消费者必须知悉的信息量。此处"最小化"指减少所暴露的复杂性，而非减少代码量。

## 2. 复杂性

定义：复杂性指软件系统结构中一切使其难以理解或修改的属性（APoSD 第2章）。其度量取决于理解与修改的
代价，而非代码规模。

症状有三：

- **变更放大**：单一需求变更需在多处修改。在多 Agent 系统中表现为改动分散至大量文件与 PR，扩大人类
  监督者的审查面。
- **认知负荷**：完成某任务所需掌握的知识总量。增加代码行数未必增加复杂性；若其降低读者需掌握的知识量，
  则整体更简单。
- **未知的未知**：消费者无法预先判定需修改何处、何种改动将引发故障。此为最严重症状，对应人类监督者对
  Agent 行为的不可见性。

根源有二：**依赖**——代码无法被独立理解或修改，其变更须连带修改他处；**模糊**——关键信息不明显，
包括命名不当、文档缺失、约定不一致。第 4–5 节与第 6 节分别针对此二者。

复杂性由大量微小增量叠加形成，而非单一错误所致，故须对新增复杂性采取零容忍。

## 3. 设计立场

能通过测试的代码不足以构成良好设计（APoSD 第3章）。战术式编程仅以功能可用为目标，持续累积设计债；
战略式编程将设计质量列为并行目标，主张持续投入（书中建议约占开发时间的 10–20%），以换取后续开发速度。
其推论：

- 每次修改现有代码，应使系统结构趋近于"依当前认知从零设计所应有的形态"（APoSD 第16章），避免"仅
  追加、不重构"的最小改动。
- 关键设计决策应生成两个及以上根本不同的方案并比较优劣，即"设计两次"（APoSD 第11章）。

在多 Agent 系统中，Agent 产出速率高、并发度大，战术式产出所累积的设计债将以并发速率增长并超出人类
审查能力，故应令 Agent 默认采用战略式产出。"设计两次"可由多个 Agent 并行生成候选方案后择优。

## 4. 降低依赖（一）：深模块与信息隐藏

模块由**接口**（消费者使用它所需付出的认知成本）与**实现**（其所提供的功能）构成。**深模块**指以简单
接口封装大量功能的模块；**浅模块**指接口复杂度接近或超过其所封装实现的模块（APoSD 第4章）。将功能
过度切分为大量小模块（classitis）会产生浅模块，增加消费者需掌握的接口总量，从而提高整体复杂性。接口的
简单性优先于实现的简单性，因实现者数量远少于消费者。示例：Unix 文件 I/O 以 `open`/`read`/`write`/
`lseek`/`close` 五个调用封装磁盘调度、缓存、块分配与设备差异。

多 Agent 推论：一个 PR 宜构成深模块——其接口为意图、结果与待决策项，其实现为文件级 diff；人类监督者
仅需读取接口。

构造深模块的技术如下。

**信息隐藏**（APoSD 第5章）：每个模块封装一项设计决策，使其仅存在于实现、不出现于接口。其反面为
**信息泄漏**——同一设计决策反映于多个模块，导致其变更须同步修改多处，即变更放大的成因。多 Agent 推论：
对人类监督者应隐藏实现过程、暴露决策与权衡；RFC/spec 承担"设计决策单一记录"的职能，防止其泄漏至
代码各处。

**避免时序分解**（APoSD 第5章）：时序分解指依操作执行的时间顺序划分模块，导致同一知识被分散至多个
模块。模块划分应依据完成各任务所需的知识，而非其执行次序。

**复杂性下移**（APoSD 第8章）：面对某处复杂性，应优先由实现承担而非转移至接口，因消费者多于实现者。
可默认或可自动推断的配置，不应设为须消费者决定的参数。

**适度通用**（APoSD 第6章）：适度通用的实现通常具有更简单的接口且可复用。经验准则为接口通用至可支持
多种用法、实现仅满足当前需求，且不应过度通用至妨碍当前使用。

**分层的抽象差异**（APoSD 第7章）：相邻层应提供不同抽象。**穿透方法**（仅将参数转发至下层、不增加
功能的方法）与**穿透变量**（贯穿多层传递而中间层并不使用的参数）均为分层不当的信号。

**合并与拆分判据**（APoSD 第9章）：两段功能满足以下任一条件时倾向合并——共享信息、总被一起使用、
概念上可归入同一更高层类别、合并可消除重复；否则倾向拆分。不应仅以缩小文件为由而拆分。**联体方法**
（须同时理解方能读懂彼此的两个方法）为过度耦合的信号。多 Agent 推论：RFC 子任务与文件划分的依据应为
认知独立性，即单个 Agent 可独立理解并完成；过细划分增加 Agent 间的对齐成本，过粗划分降低并行度。

## 5. 降低依赖（二）：消除错误

减少异常处理的首选手段为重新定义操作语义，使异常情形不再构成错误（APoSD 第10章），因每个异常均为
消费者须额外掌握的一条执行路径。示例：将"删除变量"定义为"确保变量不存在"，则删除不存在的变量无须
报错；将字符串截取定义为"返回落在有效范围内的字符"，则下标越界不再抛出异常。设计接口时应评估各错误
情形可否经语义重定义予以消除。消除一类错误即减少消费者须掌握的一条特殊路径。

## 6. 降低模糊：使代码显而易见

代码应显而易见，即读者无须停顿推测即可理解其行为（APoSD 第18章）；模糊为复杂性两根源之一，亦为
未知的未知之来源。降低模糊依靠以下三项。

**注释**（APoSD 第13章）：注释应记录代码本身不显现的信息，重点为设计意图（why）与抽象层面的功能
描述；不应复述代码，接口注释不应包含调用者无须知悉的实现细节。注释应先于实现编写，作为设计过程的
组成部分（APoSD 第15章）；某单元的注释难以清晰表述，表明其抽象设计尚未成熟。多 Agent 推论：注释为
后续 Agent 的低成本上下文来源；依 OpenAgents 约定，代码注释引用对应 RFC ID，以建立代码至设计依据的
索引。

**命名**（APoSD 第14章）：名称应具备精确性（指称范围足够狭窄）与一致性（同一含义始终使用同一名称）。
名称模糊、或难以确定精确名称，通常指示相应实体职责不清。此约束同样适用于分支、PR、issue 与 RFC 的命名。

**一致性**（APoSD 第17章）：相似事物以相似方式处理、相异事物以相异方式处理。一致性降低认知负荷，使
消费者可据既有模式推断行为。违背既有约定较之缺乏约定更为有害，因其诱导基于表面相似的错误假设。
多 Agent 推论：不同 Agent 可能由不同 coding agent 驱动，其产出的可组合性依赖强一致的约定；软性约定在
多 Agent 环境下易被破坏，宜以 schema 与校验规则予以强制。

## 7. 对趋势与性能的评估

评估软件趋势的统一标准为其是否降低复杂性，而非是否新颖（APoSD 第19章）。书中判断：接口继承有益，
实现继承因引入类间依赖与信息泄漏而须审慎；单元测试有益，因其支持安全重构；测试驱动开发被判为战术式
编程，因其聚焦于单个功能而非整体设计；设计模式恰当使用有益、生搬硬套构成过度工程；getter/setter 为
浅方法且削弱信息隐藏。同一标准适用于多 Agent 编排等新方法。

性能（APoSD 第20章）：应先采用简单设计，简单设计通常亦具较优性能。优化应基于测量识别关键路径，仅在
其上引入复杂性，并将该复杂性封装于深模块内，避免其泄漏至接口。

## 附一：设计原则清单（APoSD 书末总结）

1. 复杂性是渐进的，须处理每一处小的复杂性。
2. 能通过测试的代码不足够。
3. 持续做小额投资以改进系统设计。
4. 模块应该是深的。
5. 接口应设计为使最常见的用法尽可能简单。
6. 模块接口的简单性比实现的简单性更重要。
7. 通用模块更深。
8. 通用代码与专用代码应分离。
9. 不同的层应具有不同的抽象。
10. 将复杂性向下移。
11. 将错误（及特例）定义为不存在。
12. 设计两次。
13. 注释应描述代码中不显现的信息。
14. 软件应为易于阅读而设计，而非易于编写。
15. 软件开发的增量应为抽象，而非功能。

## 附二：红旗清单

出现下列信号时应暂停并重新审视设计。书中列举 14 项（括号内为判据）：

浅模块（接口未显著简单于实现）、信息泄漏（一项设计决策反映于多个模块）、时序分解（结构依执行顺序而非
信息隐藏划分）、过度暴露（接口迫使调用者了解罕用特性）、穿透方法（仅转发参数而不做实质工作）、重复
（非平凡代码反复出现）、专用-通用混杂（专用代码未与通用代码清晰分离）、联体方法（两方法依赖过深、
无法独立理解）、注释复述代码（注释信息由相邻代码即可获知）、实现文档污染接口（接口注释包含调用者
无须知悉的实现细节）、名称模糊（名称不精确、传达信息不足）、难以命名（无法确定精确直观的名称）、
难以描述（须冗长文档方能说明完整）、代码不显而易见（行为或含义不易理解）。

本文档就多 Agent 系统补充四项（属演绎，非原书内容）：

- **冗余编排层**：增加编排层级而不产生新抽象（对应穿透方法）。
- **审查放大**：单一改动分散为大量待审文件或 PR，超出人类审查能力（对应变更放大）。
- **上下文溢出**：单个 issue 或 RFC 的上下文无法容纳于一个 context window（对应认知负荷）。
- **单次设计**：关键接口未执行"设计两次"。

## 附三：应用

1. 划分模块与确定接口时，依次应用深模块、信息隐藏、复杂性下移三项原则，并明确接口消费者必须知悉的
   最小信息集。
2. 判定某设计"可运行但欠优雅"时，对照附二红旗清单逐项检查，命中则重新设计。
3. 对关键接口执行"设计两次"，必要时由多个 Agent 并行生成候选方案后择优。
4. 撰写 RFC、PR 与评论时，将其视为面向人类监督者与后续 Agent 的深模块接口，仅暴露决策、权衡、成果与
   待决策项，隐藏实现细节。
5. 验收判据：该设计是否已将人类监督者与后续 Agent 必须知悉的信息量降至最小。
