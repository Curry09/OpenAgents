# OpenAgents Specs

This directory records design decisions and tracks their implementation. Each Spec group is a Markdown
file named `NNNN-slug.md`. Its YAML frontmatter holds structured metadata and a dependency graph of
tasks. The body is a self-contained design overview in the style of the [Rust RFCs](https://github.com/rust-lang/rfcs).

See the [project README](../../README.md), [configuration guide](../CONFIGURATION.md), and
[architecture guide](../ARCHITECTURE.md) for current usage and module boundaries. Earlier Specs may
describe retired modules or historical verification procedures. The
[original Chinese texts](../specs-zh-CN/README.md) are preserved separately.

## When to write a Spec

Write a Spec for a new component, a public interface or protocol change, a persistence change, a feature
spanning modules, or any change with a design trade-off worth recording. A small change can skip a new
Spec when it has no design decision to record, affects only one module or file, and needs a single task.
If the work naturally extends an existing Spec, add a task to that group.

## What to include

A reader should be able to understand a Spec by itself. Restate the essential context when citing other
Specs. Use the section headings generated by `spec new`:

| Section | Content |
| --- | --- |
| Summary (required) | A short description of the feature. |
| Motivation (required) | Current behavior, the problem, and why it needs a change. |
| Guide-level explanation | How to use or explain the feature, with examples. |
| Reference-level explanation (required) | Technical design, task dependencies and file allocation, and the path to end-to-end verification. |
| Drawbacks | Costs or reasons to leave the design unchanged. |
| Rationale and alternatives (required) | Why this design was chosen and at least one alternative that was rejected. |
| Prior art | Relevant designs in other projects or publications. |
| Unresolved questions | Open decisions and unknowns. |
| Future possibilities | Natural extensions. |

Each frontmatter task has an ID, title, status, priority, dependencies, owned files, scope, and
acceptance criteria. Each task must declare its files, and tasks in the same group must not claim
the same file. See the [task field reference](../../.claude/skills/spec-driven-development/references/task-fields.md).

Tasks move from `pending` to `in-progress` to `done`. Completed tasks remain as a map to the live
code. `spec abandon` removes abandoned tasks; their history remains in Git. Dated design records
(`YYYY-MM-DD-topic-design.md`) describe design history and do not reserve a group number.

## Update a Spec

```bash
spec new <slug> --issue <number> --title "Title" --summary "Summary"
spec add-task <group> --id T1 --title "Task title" --priority P1 --files <path> --acceptance "Acceptance criteria"
spec validate
spec render
spec graph
```

Edit the numbered Markdown file to revise its frontmatter or design sections. Regenerate
[OVERVIEW.md](OVERVIEW.md) and [ARCHITECTURE.md](ARCHITECTURE.md) with the CLI; CI checks for drift.
Use `spec graph --check` to check the architecture view and module docstrings.

In a shared repository, `spec new` reserves the group number in the remote `spec-reservations/NNNN`
namespace. If the remote is unavailable, resolve that before creating a group. Local-only repositories
allocate the next number locally. If a PR's number conflicts, run `spec reserve-number --issue <number>
--slug <slug>` before renumbering. CI checks the numbers against other open PRs.

See the [Spec workflow](../../.claude/skills/spec-driven-development/SKILL.md) for design and review steps.
